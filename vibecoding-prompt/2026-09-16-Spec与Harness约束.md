# Spec 与 Harness 约束

## 用户原话

“可以 请给我spec文档 以spec把架构全部定好了 每个任务的接口定义、目录结构、模块交互方式全部写死。AI 的角色是‘按图施工’，没有设计决策权。从源头杜绝了 AI 自由发挥导致的架构混乱。开发遵从Harness思想。Agent 用完即销毁——每个任务一个独立会话，完成就销毁，防止上下文污染和错误传播。权限边界明确——AI 只能操作 Spec 指定的文件，不允许自行创建模块或修改架构。”

## 已确认决定

- 承接“可以”：差异先采用待核实/已处理＋备注的轻量方式，不执行补货/退款等外部流程。
- 要求先交付完整Spec，固定架构、模块接口、目录和任务权限。
- 开发使用单任务新会话，执行者无架构决策权，完成后结束会话和工具访问；不同任务不继承聊天上下文。
- 未列入任务文件白名单的模块和架构禁止修改。

## 本次交付

在实际项目spec/创建IR-SIMPLE-1.0.0规范包：产品状态、架构与8张表、15个HTTP接口与Python/前端模块契约、确定性规则、12个任务及81个精确实现路径、Harness协议、30个业务场景与6个Harness验收要求、基线hash和自审记录。

没有实施业务代码、创建开发会话、迁移数据库或提交推送。当前中文界面未提交，执行前需负责人纳入新基线。Spec中作者固定的具体技术选择尚待负责人审阅冻结；实现Agent不得自行调整。

## 约束的实际含义

提示词和文件差异检查不能替代OS文件系统隔离。Spec区分filesystem-isolated与diff-gate-only，正式接纳要求可信宿主提供前者；T00实现仓库守卫，不能伪称已具备宿主权限隔离。销毁Agent指终止会话复用、进程和工具访问，保留审计证据，不自动删除用户任务历史。
