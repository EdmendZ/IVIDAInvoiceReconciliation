# Invoice 与 Receive Note 流程讨论

## 用户原话与确认

“暂时先不加入合同内容 依然是invoice和reveive note 适用superpower和我讨论 之前的项目结构、项目设计是否合理，流程是否冗余”

已确认：暂不加入合同，保持 Invoice 与 Receive Note 范围。当前授权 Superpowers 参与设计讨论，不实施代码重构。中文界面与英文业务数据的要求继续有效。

## 初步分析（助手建议，未批准实施）

- 保留模块化单体、独立抽取 Worker、任务重试记录、不可变核对版本、原件与业务数据分离存储。
- Task/Run、机器 Draft/人工 Version、核对结果/差异处置分别表达不同责任，并非对象多就是冗余。它们无需全部成为用户可见步骤。
- 当前上传、审核、核对、差异处理分散在多个工作区，可能增加同一操作人的切换与重复定位成本。
- 单据审核确认的是抽取是否正确；差异处置确认的是实际业务差异如何处理，不能直接视为重复审核。但不一定要让用户跨页面、分两次完成。
- Receive Note 若来自可信的上游结构化收货记录，应继续绕过 OCR 和重复人工字段审核；上传的外部单据仍需建立可信度。
- 对无价格的收货单应明确仅核验数量，不能凭数量一致声称单价/金额已核验，也不能自动把全部缺价当错误。
- Reviewer 认领、提交、Admin 批准/退回适用于职责分离；若主要是一人处理，则可能过重。质量评测是研发工具，宜与日常作业分开入口。
- 选项：保持多人审批流程；保留底层治理、整合成简洁单人工作台（倾向建议，取决于角色）；只做上传比较工具（简单但削弱追溯与真实流程，不优先推荐）。

## 本轮解释与建议（具体交互待确认）

- “等待提取”是后台 OCR/模型把 PDF 或图片转换为结构化字段的时间，不应成为用户手动推进的环节；上传后自动处理并在原页面显示进度，结构化收货记录绕过提取。
- “切到对账”是当前页面分区造成的导航操作，不是业务必需。建议发票详情内直接展示候选收货记录与自动核对预览。
- 系统可自动生成候选关联与核对预览，但不能凭启发式高分就最终确认收货关联。明确关联也应可见、可纠正；候选有歧义时只让用户处理必要选择。
- 认领/改派用于多人分工，单人模式无需单独认领、另交管理员审批。仍保留操作人和历史记录，不把已确认业务差异当成不存在。
- 提议交互为：上传发票 → 后台提取并展示核对预览 → 用户在一页检查重点并确认；有差异时同页选择处理方式。确认时冻结经确认的字段版本与关联，再执行最终规则并保存快照，保持预览与正式结果的区别。
- 当前代码只允许可信批准版本正式核对；“草稿自动预览”是待设计能力，不能宣称现已实现。

## 单页流程继续讨论

用户回复：“好 请继续”。承接上一轮问题，确认首页采用“上传发票＋待处理发票列表”，进入一张发票后在同一页完成操作。继续细化设计，尚未执行开发。

助手提出的交互细节（待确认）：

- 首页用业务状态展示处理中、待确认、待处理差异、已完成；系统失败单独提示重试，不将模型技术阶段全部列成操作入口。
- 发票详情同页包含原件/结构化字段、关联收货记录、差异预览。通常只检查结果并确认；匹配有歧义时更换收货单，识别错误时修改字段并自动刷新预览。
- 一对多收货继续支持；系统预选并不等于正式建立财务关联。存在未解决的提取或关联问题时不允许确认完成。
- 最终确认保存不可变版本、关联与正式核对结果；等待补货或联系供应商属于未结束状态，不能点完即标记已完成。
- 差异的简化处置选项及底层 Case 状态映射还需设计；目前没有更改现有审批状态机。

下一项需澄清：收货事实主要来自 TapTouch 结构化记录，还是用户上传的外部 Receive Note 文件。该答案决定单据入口与人工审核负担；已有原型接口不代表真实 TapTouch 已接通。

## 自动匹配与一次确认：后续已确认

用户澄清原话：“不是我一开始就匹配好再上传 而是上传之后等另一个到了再上传 自动取匹配是吗”。解释后用户回复“好的 那你继续吧”。

已确认主流程：Invoice 与 Receive Note 可先后进入系统，无需用户提前配对；新单据到达后自动尝试关联并生成核对预览，另一方未到时保持等待。关联不明确时由用户确认，存在差异时由用户处理。一对多收货关系继续保留。这里是目标设计，不代表当前实现已支持自动触发匹配。

助手提出 A“先保留一次确认：一致时快速确认，异常时详细处理”与 B“一致就自动完成”。用户回复：“A”。

已确认采用 A：自动匹配和比对后，即使结果一致，也保留一次人工最终确认；不自动完成业务核对。该确认应涵盖提取字段与收货关联，不重复设置独立字段批准、手动启动对账和管理员审批等日常操作。

助手建议的确认边界：确认时服务端校验当前字段、关联和版本，固定正式结果；若输入已更新，刷新预览并要求重看。价格未知或关联存在疑问时不得标成全部一致。等待另一方单据本身不算异常；已有终态结果不因新单据静默改写。

下一项讨论：实际业务差异是否先采用轻量的“待核实/已处理＋备注”方式，而非在原型里管理补货、退款、贷项单等执行流程。此项尚未确认。
