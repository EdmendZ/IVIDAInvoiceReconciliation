# 面试复习手册

## 30 秒版本

> 我做了一个 Invoice 与 Receive Note 的 AI 辅助审核 Pilot。MinerU 负责解析
> PDF 版面和表格，LLM 将结果归一化为带 Evidence 的业务 Schema。模型结果
> 先经过 Pydantic 和财务规则验证，再由人工创建不可变批准版本。最终一张
> Invoice 可以与多张 Receive Note 聚合核对，差异由确定性 Python 规则给出。
> 项目还保存模型、Prompt、Token、延迟和成本，并用缓存的合成 Gold 数据做
> 模型对比。

## 两分钟版本

按“问题—设计—结果—边界”讲：

1. 问题：发票与收货单模板不统一，且存在一对多分批收货；
2. 设计：MinerU 解析、LLM 归一化、规则验证、人工批准、规则核对；
3. 工程：FastAPI + 独立 Worker + PostgreSQL + MinIO + React；
4. 大模型：Prompt 指纹、Schema、Evidence、Token/延迟/成本、缓存评测；
5. 结果：真实 API 链路和单文档冒烟已跑通；
6. 边界：合成数据、单 Worker、没有四眼审批和高可用。

## 高频问题与回答思路

### 为什么不用一个视觉大模型直接完成

不是不能用，而是当前两阶段链路更容易隔离 OCR 与归一化错误、复用解析缓存、
保存文本 Evidence 和独立替换模型。视觉模型会作为同 Gold 数据集上的对照组，
用准确率、延迟和成本决定，而不是凭印象排除。

### 为什么不用本地模型

Pilot 优先验证业务闭环和质量基线，公共 API 减少部署时间。是否本地化取决于
数据合规、吞吐、GPU 利用率、延迟和总成本。Provider 接口已经隔离模型实现，
后续可接私有 OpenAI-compatible 服务。

### 为什么使用 MinerU

它专注文档解析、版面和表格，输出 Markdown/blocks/tables，适合后续结构化。
但它不是不可替换依赖，Parser Protocol 允许替换。

### 为什么 PostgreSQL，不用 MongoDB

业务以关系、状态机、版本、外键和审计为主，需要事务与条件更新。MongoDB
适合某些文档型场景，但这里不会带来明显优势。MinIO 已承担二进制对象存储。

### queued 为什么不直接用消息队列

单 Worker 本机 Pilot 使用 PostgreSQL 轮询可以复用已有事务与持久化，减少
演示依赖。多 Worker、高吞吐和独立弹性出现后才引入消息代理和 fencing。

### 如何防止模型幻觉

不是“防止所有幻觉”，而是分层降低风险：

- JSON Mode 和 Pydantic Schema；
- 关键字段 Evidence；
- 文档内部算术校验；
- 人工确认单据类型和原文；
- Approved Version 门禁；
- 最终核对不用 LLM。

### 为什么编辑要创建版本

财务结果必须能回答模型原始输出、谁修改、为什么修改、批准的是哪一版。覆盖
同一 JSON 会破坏审计链。

### 候选分数是否是概率

不是。它是基于 PO、供应商、门店、币种、日期和商品重叠的可解释规则分。
高分不代表统计意义上的 85% 概率。

### 如何处理一张发票对应多张收货单

先将所有已选收货单的商品行按 SKU/描述聚合，再比较总数量、加权单价和金额。
不能逐张与整张发票比较。

### 如何评价模型

使用合成 Gold 数据，报告 Schema 通过率、字段 micro accuracy、行项目 F1、
Evidence coverage、P50/P95 延迟和成本。MinerU 结果按 SHA 缓存，使不同模型
对比只改变 Normalizer。

### 项目最大的技术债是什么

可诚实回答：

- 真实脱敏数据不足；
- 只有单文档模型冒烟，没有完成多模型全量对照；
- 单 Worker 租约没有 fencing/续期；
- 缺少四眼审批、恶意文件扫描、完整监控和灾备；
- 前端复杂交互测试仍少。

## 容易说错的地方

| 不准确说法 | 建议说法 |
|---|---|
| 系统自动审核发票 | 系统辅助抽取和初步核对，人工批准 |
| 候选 85 分就是 85% 概率 | 85 是启发式规则分 |
| 已达到生产级 | 完成本机 Pilot，生产加固项明确 |
| 模型准确率 89.47% | 一份合成发票的冒烟字段准确率 |
| 使用了三方对账 | 当前是 Invoice 对 Receive Notes 两类单据核对 |
| 取消后 MinerU 一定停止 | 本地停止后续处理，远端可能继续 |

## 白板讲解顺序

```text
原件 → Task → Run → MinerU → LLM → Draft
     → Human Review → Approved Version
     → Candidate Matching → Reconciliation Record
```

每讲一个箭头都回答：

- 谁执行？
- 状态存哪里？
- 失败怎么处理？
- 哪一步需要人工？
- 哪一步使用 LLM，哪一步不用？

## 最后总结

项目的亮点不是“调用了一个模型”，而是把不确定模型输出放入可审计业务流程：

- 输入可追溯；
- 模型和 Prompt 可追溯；
- 错误可验证；
- 人工修改可版本化；
- 最终财务差异由确定性规则计算；
- 模型选择可以用数据复现。
