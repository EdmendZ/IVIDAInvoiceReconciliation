# 文档维护规范

## 目标

文档不是开发完成后的补充材料，而是业务行为的一部分。代码和文档不一致时，
新成员会建立错误心智模型，面试时也容易描述已经过期的设计。

## 哪些修改必须同步文档

| 代码变化 | 至少更新 |
|---|---|
| 领域字段、状态、业务术语 | 业务全景或单据生命周期 |
| Worker 阶段、重试、取消 | 单据生命周期或 AI 抽取链路 |
| Prompt、Parser、Normalizer | AI 抽取链路、模型选择或评测文档 |
| 审核、版本、批准规则 | 人工审核与版本治理 |
| 候选权重、容差、聚合规则 | 候选匹配与核对规则 |
| PostgreSQL 表、迁移、MinIO 路径 | 数据与基础设施 |
| API、权限、前端操作 | API、UI 与本机运行 |
| 测试指标、Gold、评测排名 | 测试与模型评测 |
| 启动脚本、环境变量、端口 | API、UI 与本机运行及 `.env.example` |

## 注释原则

代码注释应解释：

- 为什么采用此状态或分支；
- 哪些数据不能被默认为 0/空；
- 外部调用和事务的边界；
- 并发、重试、取消和幂等行为；
- 容易被误用的业务规则。

不要添加：

- 逐行翻译语法的注释；
- 与实现重复的“创建对象”“返回结果”；
- 无法验证的生产能力；
- Token、密码、真实客户字段和值。

## 修改流程

1. 在 `docs/code-document-map.json` 找到代码所属主题；
2. 修改代码和测试；
3. 同步修改至少一份对应文档；
4. 如果引入新术语，更新 `docs/README.md` 阅读路线或术语解释；
5. 运行文档同步检查；
6. 运行后端测试、前端测试和构建；
7. 提交信息中说明行为变化，文档与代码放在同一提交。

检查命令：

```powershell
.\.venv\Scripts\python.exe tools\check_documentation_sync.py
```

比较指定 Git 基线：

```powershell
.\.venv\Scripts\python.exe tools\check_documentation_sync.py `
  --base-ref origin/main
```

## 新增功能时如何扩展文档

如果现有文档无法清晰容纳新主题：

1. 在合适的 `docs/business`、`docs/ai`、`docs/architecture`、
   `docs/operations` 或 `docs/interview` 下新增文件；
2. 文件名使用两位阅读顺序编号；
3. 在 `docs/README.md` 增加入口；
4. 在 `docs/code-document-map.json` 增加代码到文档映射；
5. 为关键路径补文档契约测试。

## 允许不更新业务文档的情况

纯格式化、拼写修正、等价重构可以不改变业务说明，但仍建议更新代码注释或
提交说明。同步脚本允许通过 `--allow-code-only` 显式跳过；这个参数应只用于
确认没有行为变化的提交，不能成为默认做法。

## Review Checklist

- [ ] 文档中的状态、端口、路径和默认值与代码一致；
- [ ] 图中没有宣称不存在的组件；
- [ ] 示例只使用合成数据；
- [ ] API Key、密码、服务器地址没有进入文档；
- [ ] 新增代码注释解释设计意图而不是翻译语法；
- [ ] 已运行文档同步检查；
- [ ] 已运行相应测试。
