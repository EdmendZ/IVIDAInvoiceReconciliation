# 产品缺口与后续路线

## 第一阶段已经解决

- 外部 Invoice/Receive Note 文件继续走抽取、证据和人工批准；
- Taptouch Receiving 可通过受保护接口直接形成权威不可变版本；
- 当前版本重放幂等，同版本篡改和旧版本会被拒绝；
- 上游作废会从新候选中移除该 Receiving；
- 候选页显示来源、门店、外部记录 ID、版本和上游更新时间；
- 一张 Invoice 仍可选择多张 Receive Note 进行确定性核对。

## 上真实环境前的必要缺口

### 1. 租户与门店授权

当前 Bearer Token 是单一原型凭据，不能表达“哪个调用方能写哪些 tenant/store”。
真实集成需要凭据主体、允许范围、吊销、轮换和审计，并让查询也受到相同租户边界
约束。

### 2. 可靠事件交付

当前由调用方直接 POST。真实系统需要定义重试退避、死信、告警、事件追踪 ID、
Schema 版本兼容和批量补数流程。

### 3. 重复发票识别

同一供应商可能重复上传发票。后续应以 tenant/store、供应商、发票号、日期、金额
和文件 Hash 组合识别“完全重复”与“疑似重复”，但不能仅凭发票号自动删除数据。

### 4. 部分收货分配

现有一对多核对会聚合选中的完整 Receive Notes。真实业务可能需要把一张收货单的
部分行或数量分配给不同发票，并防止累计分配超过实际收货量。

### 5. 简单与企业工作流

小门店需要低操作成本，复杂组织需要职责分离、SLA、批量处理和审批策略。后续可
提供 Simple/Enterprise 模式，但两者必须共享同一底层事实和审计模型，不能复制两套
业务状态机。

## 明确的优先顺序

若项目继续向真实 Taptouch 集成演进，推荐顺序是：

1. 获取并验证真实 Receiving API/事件契约；
2. 实现 tenant/store 范围的身份与授权；
3. 完成可靠投递、告警、补数和凭据轮换；
4. 加入重复发票检测；
5. 用真实业务样本验证部分收货分配是否必要；
6. 最后再根据用户规模设计工作流模式。

PO 创建、付款、会计总账和库存主数据仍应由相应上游系统负责，除非 IVIDA 明确
把这些能力纳入本项目边界。
