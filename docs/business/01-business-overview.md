# 业务全景：为什么要核对 Invoice 和 Receive Note

## 先建立直觉

餐厅向供应商采购面粉、番茄酱、芝士等原料时，至少会产生两类单据：

- **Invoice（发票）**：供应商声明“我向你收多少钱”；
- **Receive Note（收货单）**：门店声明“我实际收到了什么”。

真正需要核对的不是两张图片是否相似，而是两个业务事实是否一致：

> 供应商要求付款的商品、数量、单价和金额，是否能被实际收货记录支持？

## 为什么不是简单的一对一

一张采购订单可能分批到货，因此常见关系是：

```text
Invoice INV-1001
  ├─ Receive Note RN-2001：周一收到面粉和番茄酱
  └─ Receive Note RN-2002：周三补到芝士
```

核对时必须先把两张收货单的相同商品聚合，再与发票比较。如果强制一对一，
每张收货单都会被误判为“数量不足”。

## 项目解决的四个问题

### 1. 非结构化单据如何变成业务字段

供应商模板不同，PDF 可能是扫描件，表格结构也不统一。项目先用 MinerU
解析版面和表格，再让 LLM 映射到统一的 `Invoice` / `ReceiveNote` Schema。

### 2. 模型结果如何被信任

模型输出只是 Draft。每个重要字段携带原文证据，系统再做 Schema 和金额规则
检查。审核人员确认单据类型、证据和错误后才能批准。

### 3. 哪些收货单可能属于这张发票

系统根据采购订单号、供应商、门店、币种、日期和商品重叠程度计算候选分数。
候选分数只是解释性推荐，不会自动建立不可撤销的财务关系。

### 4. 最终差异如何判定

批准后的结构化版本进入确定性 Python 规则：

- 相同 SKU，或缺少 SKU 时使用标准化描述作为商品键；
- 聚合所有 Receive Notes 的同一商品；
- 比较数量、加权单价和金额；
- 根据容差输出 exact、within tolerance、mismatch 等状态。

## 参与者与职责

| 参与者 | 在系统中的职责 |
|---|---|
| 门店/采购人员 | 上传单据，提供必要的采购订单提示 |
| MinerU | 解析 OCR、版面、表格和 Markdown |
| LLM | 将解析结果归一化为业务 Schema，并生成字段证据 |
| 规则引擎 | 校验金额关系、计算候选分数、执行最终核对 |
| 审核人员 | 核对原文、修改草稿、确认类型、批准或驳回 |
| PostgreSQL | 保存任务、版本、动作和核对结果 |
| MinIO | 保存原始文件和 MinerU 产物 |

## 业务边界

当前系统做的是 **pre-reconciliation（初步核对）**：

- 可以指出数量不足、价格不同、发票独有商品、收货单独有商品；
- 可以保存审核证据和模型运行信息；
- 不连接银行，不触发付款；
- 不替代会计审批；
- 不声称满足特定国家或企业的全部财务合规要求。

## 一个贯穿文档的例子

假设发票 `INV-1001` 包含：

| SKU | 商品 | 数量 | 单价 | 金额 |
|---|---|---:|---:|---:|
| FLOUR | Pizza flour | 10 | 20.00 | 200.00 |
| CHEESE | Mozzarella | 5 | 30.00 | 150.00 |

两张收货单分别记录：

- `RN-1`：FLOUR 6、CHEESE 5；
- `RN-2`：FLOUR 4。

聚合后 FLOUR 为 10，CHEESE 为 5，因此数量可以完全匹配。项目中的
`app/services/reconciliation_service.py` 正是先聚合、后比较，而不是逐张
收货单直接比较。

## 面试复习点

1. 业务关系是一张 Invoice 对多张 Receive Note。
2. LLM 解决“理解和归一化”，规则解决“计算和判定”。
3. Draft 不等于可信数据，Approved Version 才能进入核对。
4. 候选推荐与最终核对是两个不同阶段。
5. Pilot 的目标是提高人工审核效率，不是无人审批。
