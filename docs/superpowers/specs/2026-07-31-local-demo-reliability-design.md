# IVIDA 发票核对本机演示可靠性设计

## 目标

让非开发人员在一台 Windows 电脑上，通过一个入口启动并演示完整业务链路：

`上传 → MinerU 解析 → 模型结构化 → 人工审核 → 批准 → 候选配对 → 核对差异`

本阶段解决演示中最明显的运行问题：

- 操作者忘记启动 Worker 后，任务长期显示 `queued`，但界面没有解释原因。
- API、Worker、前端需要分别启动，启动顺序和失败位置不直观。
- 排队任务没有取消入口。
- 技术状态名称不能准确告诉业务操作者下一步该做什么。

本阶段不改变财务核对规则，不引入新的云服务，不将 Worker 嵌入 API，也不实现对 MinerU 远端作业的强制终止。

## 总体方案

保留三个可独立重启的应用进程：

1. FastAPI：提供上传、审核、核对和运行状态接口。
2. Extraction Worker：消费 PostgreSQL 中的持久化任务，调用 MinerU 和结构化模型。
3. Vite 前端：提供本机演示操作界面。

新增一个 PowerShell 演示启动器统一完成配置检查、端口检查和进程启动。进程仍保持独立，因此 Worker 崩溃不会带走 API，API 热重载也不会重复创建 Worker。

PostgreSQL继续作为任务、运行记录、审核版本和核对结果的事实来源；MinIO继续保存原件和解析产物。

## 一键启动

新增根目录脚本 `start_local_demo.ps1`：

1. 定位项目根目录和项目虚拟环境。
2. 检查 `.env`、Python、Node 依赖和必填配置是否存在，但不输出密钥。
3. 检查 `8200` 和 `5274` 端口。
4. 检查 PostgreSQL 与 MinIO 是否可访问。
5. 分别启动 API、Extraction Worker 和前端。
6. 等待 API 健康检查与前端端口就绪。
7. 输出每个组件的状态、日志位置和访问地址。

启动器发现端口已被本项目组件占用时，不重复启动该组件；发现端口被未知进程占用时，明确报错并停止，不自动结束用户进程。

新增配套的 `stop_local_demo.ps1`。它只停止由启动器记录的本项目进程，不根据端口盲目终止进程。

## Worker 在线状态

Worker 每隔固定时间向 PostgreSQL 写入心跳，记录：

- `worker_id`
- `started_at`
- `last_seen_at`
- 当前版本或进程标识

API 根据最近一次心跳判断 Worker 状态：

- `online`：心跳仍在有效窗口内。
- `offline`：不存在心跳或心跳已过期。

健康接口不因 Worker 离线而将整个 API 标记为不可用。前端在上传页显示独立提示：

- `Worker online`：任务将自动处理。
- `Worker offline — tasks will remain queued`：任务已安全保存，但不会开始抽取。

此设计避免依靠“数据库中是否有任务正在变化”来猜测 Worker 是否存活。

## 任务状态展示

后端继续保存稳定的机器状态，前端将它们转换为面向操作者的文案：

| 机器状态 | 中文显示 | 操作者含义 |
|---|---|---|
| `uploaded` | 已上传 | 原件已保存，可以开始处理 |
| `queued` 且 Worker 在线 | 排队处理中 | Worker 将自动领取 |
| `queued` 且 Worker 离线 | 等待处理服务启动 | 需要启动 Worker |
| `parsing` | 文档解析中 | MinerU 正在识别文档 |
| `normalizing` | 字段提取中 | 模型正在生成财务字段 |
| `ready_for_review` | 等待人工审核 | 可以进入 Review |
| `failed` | 处理失败 | 查看原因后重试 |
| `cancelled` | 已取消 | 不再继续后续处理 |

界面显示任务级状态和最新运行状态，但以最新运行状态作为当前处理进度，避免出现任务与运行记录互相矛盾。

## 取消语义

本阶段采用协作式取消，不尝试杀死 Python 线程或强制终止 MinerU 远端作业。

### 可以取消的状态

- `queued`：立即标记运行记录和任务为 `cancelled`。
- `parsing`：记录取消请求；Worker 在下一次轮询前检查并停止后续处理。
- `normalizing`：记录取消请求；如果模型调用已经开始，允许当前调用返回，但不创建审核草稿。

### 不允许取消的状态

- `ready_for_review`
- `succeeded`
- `failed`
- `cancelled`

这些状态已经是终态或已进入人工治理阶段。需要放弃审核内容时，使用现有驳回流程，而不是取消抽取任务。

取消不删除：

- MinIO 原件
- 已保存的 MinerU 解析产物
- PostgreSQL 任务、运行记录和错误信息
- 审计字段

因此取消操作可追踪，也不会造成数据库和对象存储之间难以恢复的部分删除。

## API 与数据变更

新增：

- Worker 心跳表及对应 repository。
- Extraction Run 的 `cancelled` 终态、取消请求时间和取消完成时间。
- `GET /api/runtime/status`：返回 API、Worker、PostgreSQL 和 MinIO 的脱敏状态。
- `POST /api/extraction-runs/{run_id}/cancel`：请求取消当前运行。

取消接口必须：

- 需要已登录的 reviewer 或 admin。
- 支持幂等重复调用。
- 对不可取消状态返回 `409 Conflict` 和可读原因。
- 不接受客户端直接指定目标状态。

上传和开始抽取接口保持兼容。

## 前端变更

Upload 页面新增：

- 顶部运行状态条。
- Worker 离线时的明确说明。
- 可取消状态任务的“取消”按钮。
- 取消确认对话框。
- 操作者友好的中英文状态映射，本阶段先保持现有英文页面结构，并确保关键提示可理解。
- “重试”继续只针对失败任务。

取消请求期间禁用重复操作；成功后立即刷新任务列表；失败时保留任务并展示后端返回原因。

## 错误处理

- PostgreSQL 不可用：启动器停止启动并明确指出数据库连接失败。
- MinIO 不可用：启动器提示失败；API仍可单独诊断，但演示启动不进入“成功”状态。
- MinerU 或结构化模型配置缺失：启动器将其标为配置错误，不输出 Token。
- Worker 崩溃：API和前端保持可用，运行状态在心跳过期后变为离线，任务保留在 PostgreSQL。
- Worker恢复：未取消且符合领取条件的任务继续处理。
- 取消与 Worker 同时领取：repository 使用事务条件更新，最终只能进入“已领取继续检查取消”或“成功取消”之一；Worker在每个外部阶段边界再次检查取消标记。

## 本机演示验收

演示环境满足以下条件才算完成：

1. 一个脚本可以启动 API、Worker 和前端，并显示访问地址。
2. Worker 未运行时上传文档，界面明确显示“等待处理服务启动”，而不是无解释地长期 `queued`。
3. 启动 Worker 后，持久化排队任务能够继续处理。
4. 排队任务可以取消，刷新页面后仍显示已取消。
5. Worker处理中的任务提交取消后，不再创建可审核草稿。
6. 一组澳洲披萨门店测试 Invoice 和 Receive Note 能完整走到核对结果。
7. 停止脚本不会终止不属于本项目的进程。

## 测试策略

- Repository 测试：心跳有效期、取消条件更新、并发领取与取消。
- Worker 测试：每个阶段边界响应取消；取消后不创建草稿。
- API 测试：鉴权、幂等、不可取消状态和运行状态脱敏。
- 前端测试：Worker 在线/离线提示、取消按钮可见条件和错误反馈。
- 启动器烟雾测试：配置缺失、端口冲突、已有本项目进程和正常启动。
- 手工端到端验证：使用项目内被 Git 忽略的合成澳洲业务样本完成一次完整演示。
